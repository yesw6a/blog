# 日常博客日更全流程 SOP

## 1. 目的与权威来源

本 SOP 规定每日文章从选题到静态发布的执行顺序。以下文档分别承担唯一职责：

- `docs/article-writing-rules.md`：文件名、Frontmatter、MDX、资料和 AIGC 规则。
- `docs/article-content-architecture.md`：内容索引、静态分页、标签、搜索、RSS 和 sitemap 架构。
- `content/sop.md`：日常操作顺序、质量门禁、异常处理和发布报告。

发现三者与实际代码不一致时，应停止发布并先修正规则或实现，不得临时绕过检查。

## 2. 核心原则

- **MDX 唯一来源**：文章只存放在 `content/articles/**/*.mdx`，不手工编辑派生索引。
- **按月归档**：文章必须放在与 `publishedAt` 一致的 `content/articles/YYYY/MM/`，不得按分页目录拆分源文件。
- **先草稿后发布**：创作阶段使用 `draft: true`，全部检查通过后才改为 `false`。
- **事实可核验**：重要事实、数据和引语必须有可靠来源，不虚构日期、经历或评价。
- **分类可统计**：每篇文章必须填写稳定的 `category`，不能只依赖 tags 推断主题。
- **静态发布**：新增文章必须通过完整构建，确认详情、分页、标签、搜索、RSS 和 sitemap 能同步生成。
- **安全自动化**：可安全自动化的检查应自动执行；权限不足、仓库冲突或事实无法核验时必须停止，不得绕过权限或强制覆盖。

## 3. 主题池

| 编码 | category                | 主题                | 权重 | 单周上限 |
| ---- | ----------------------- | ------------------- | ---: | -------: |
| T1   | `ai-frontier`           | AI / 大模型前沿笔记 |  30% |     3 篇 |
| T2   | `engineering-practice`  | 前端 / 全栈工程实践 |  20% |     2 篇 |
| T3   | `tools-productivity`    | 技术工具与效率      |  15% |     2 篇 |
| T4   | `tech-industry`         | 技术产品与行业观察  |  15% |     2 篇 |
| T5   | `technical-foundations` | 深度技术原理        |  10% |     2 篇 |
| T6   | `essay-retrospective`   | 技术随笔与复盘      |  10% |     2 篇 |

权重用于合规候选之间的加权选择；周上限用于避免短期主题扎堆。所有实际发布文章，包括人工覆盖主题，都计入周统计。

## 4. 完整执行流程

### 4.1 前置环境检查

1. 进入项目目录：

   ```text
   D:\workspace\blog
   ```

2. 完整阅读：

   ```text
   docs/article-writing-rules.md
   docs/article-content-architecture.md
   ```

3. 检查仓库：

   ```bash
   git status --short
   ```

4. 状态判定：
   - 存在来源不明或与本次发布无关的修改：停止，不覆盖、不提交、不推送，并报告文件。
   - 仓库干净，或只有明确属于当前任务的修改：继续。

### 4.2 生成当日选题计划

运行只读规划命令：

```bash
pnpm.cmd content:plan -- --date=YYYY-MM-DD
```

该命令会从 MDX 元数据计算：

- 昨日发布分类。
- 本周各分类已发布数量。
- 因昨日重复或达到周上限而被排除的分类。
- 在剩余候选中按基准权重生成的可复现推荐。

正常情况下采用推荐分类。以下情况允许人工覆盖：

- 当天出现重大模型、框架、政策、论文或产品发布。
- 已完成的深度稿件需要按时发布。
- 推荐主题没有足够可靠素材。

覆盖时必须在发布报告中记录原因。禁止通过反复重跑命令挑选偏好的随机结果。

### 4.3 素材收集与证据清单

- 优先使用官方公告、规范、论文原文、项目仓库、财报和权威媒体。
- 核对来源发布日期，禁止把目标发布日期之后的信息写入文章。
- 对数字、性能、价格、发布日期、政策和直接引语逐项记录来源链接。
- 技术实践文章记录框架、工具和依赖版本。
- 无法核验的内容改写为明确观点，或更换主题，不得包装成事实。

### 4.4 创建草稿

1. 根据 `publishedAt` 创建对应年月目录，并把新文章放入：

   ```text
   content/articles/YYYY/MM/YYYY-MM-DD-short-topic.mdx
   ```

   `YYYY/MM` 必须与 `publishedAt` 一致。不要创建 `page-1`、`page-2` 等源文件目录；归档分页由构建过程自动生成。

2. 按写作规则填写完整 Frontmatter，其中：
   - `category` 使用本次计划结果。
   - `draft: true`。
   - AIGC 文章同时填写标签和元数据，正文末尾预留可见声明。

3. 正文从 `##` 开始，不重复页面标题。
4. 写作结构应匹配主题，不使用固定开场和固定章节模板。
5. 资料整理与可核验内容占主要部分，观察反思不得冒充事实。

### 4.5 草稿检查

首先运行快速内容门禁：

```bash
pnpm.cmd content:check
```

必须修复全部错误，包括：

- 文件名、年月目录、重复 slug 或保留路径。
- Frontmatter 缺失、分类错误、日期不一致。
- AIGC 三项不一致。
- MDX 语法、字符串 style 或重复 H1。

然后人工检查标题、摘要、来源、链接、图片、代码块、表格、语气和移动端可读性。

如需本地预览，由执行者按当前权限运行：

```bash
pnpm.cmd dev
```

预期访问文章详情、`/articles` 和对应标签页；预览完成后停止开发服务。

### 4.6 发布切换

人工复核通过后：

1. 将文章改为 `draft: false`。
2. 确认 `publishedAt` 不晚于当天。
3. 再次运行 `pnpm.cmd content:check`。
4. 任一检查失败时恢复修复流程，不得提交失败状态。

### 4.7 全量质量门禁

依次执行：

```bash
pnpm.cmd content:check
pnpm.cmd typecheck
pnpm.cmd lint
pnpm.cmd build
git diff --check
```

任一命令失败时：

- 立即停止提交和推送。
- 记录失败命令、文件、行号和错误信息。
- 完成修复后，从第一项重新运行全部门禁。

生产构建必须确认：

- 新文章详情页完成静态生成。
- `/articles` 出现新文章。
- 每跨越 10 篇边界时生成新的 `/articles/page/N`。
- 对应静态标签页存在。
- 静态搜索索引、RSS 和 sitemap 构建成功。
- 相邻文章导航没有指向草稿或未来文章。

### 4.8 变更范围与提交

1. 检查差异：

   ```bash
   git diff
   ```

2. 日常文章提交通常只包含：
   - 新增或修订的文章 MDX。
   - 与本次文章直接相关的资料或规则修复。

3. 不提交构建产物或手工生成的文章索引。
4. 纯文章发布不修改应用版本和 CHANGELOG；站点代码或内容系统变化才执行版本流程。
5. 创建正常提交并推送当前远程分支。
6. 禁止使用 `--force`、`git reset --hard` 或其他可能覆盖他人修改的操作。

### 4.9 发布后核验

部署完成后只读检查：

- 新文章公开 URL。
- `/articles` 及受影响的分页页面。
- 文章涉及的标签页。
- 搜索能找到标题、摘要和标签。
- `/rss.xml` 包含新文章。
- `/sitemap.xml` 包含新文章详情 URL。

发现错误时优先追加修复提交。已公开 slug 不应直接删除或重命名；确需更改时必须提供重定向。

## 5. 发布报告

最终报告必须包括：

- 文章路径和公开 URL。
- category、主题推荐结果，以及是否人工覆盖。
- 使用的主要资料来源。
- 文章总数、归档总页数和相关标签页。
- `content:check`、typecheck、lint、build、`git diff --check` 结果。
- 提交哈希、Push 和部署结果。
- 文章详情、列表、搜索、RSS、sitemap 的发布后核验结果。

## 6. 异常处理

| 场景                        | 处理规则                                       |
| --------------------------- | ---------------------------------------------- |
| 仓库存在不明修改            | 停止并报告，不覆盖、不提交、不推送             |
| 没有合规主题候选            | 停止自动选择，人工检查周上限和历史分类         |
| 当日素材不足                | 在其他合规分类中选择素材充分的主题，并记录原因 |
| 事实无法核验                | 删除该陈述、改为明确观点或更换主题             |
| Frontmatter / AIGC 校验失败 | 修复元数据和正文后重新执行全部门禁             |
| MDX 构建失败                | 优先移除可疑 JSX，改用纯 Markdown，再定位错误  |
| 未来文章意外设为公开        | 立即改回 `draft: true`，不得依赖运行时定时发布 |
| 静态分页或标签页缺失        | 停止发布，检查索引、页数和静态参数生成         |
| Push 或部署失败             | 保留本地提交，报告失败状态，不强推、不重复覆盖 |

## 7. 内容节奏复盘

- 每两周查看最近 28 天的分类实际占比，而不是累计历史占比。
- 偏差超过 ±5% 时，下一周期微调候选权重，但不修改历史文章分类。
- 每季度结合阅读数据、创作成本和素材丰富度调整权重或周上限。
- 分类语义值保持稳定；如果主题体系发生根本变化，应先设计迁移方案，再修改 Schema 和 SOP。
