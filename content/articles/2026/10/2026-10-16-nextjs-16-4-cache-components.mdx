## 一条改变了默认值的发布说明

2026 年 10 月 6 日，Next.js 团队发布 16.4 版本。官方博客用一页篇幅宣布了一件此前一直"保留意见"的事：**Cache Components 从推荐但可选，变成官方认可的首选编程模型**。从当天起，所有通过 `create-next-app` 新建的项目都会默认启用这一模型（[官方发布说明](https://nextjs.org/blog/next-16-4)）。

过去一年多，Next.js 16.x 一直在推进一套针对 App Router 痛点的编程模型：让个性化页面也能快速首屏、让服务端渲染应用拥有即时客户端导航、让缓存变成显式、声明式且可组合的能力。这套模型此前没有被全量推荐，官方说法是"有些场景还达不到旧模型的成本与性能保证"。16.4 补齐了这些差距，并把推荐状态从"适合部分应用"改为"适合每个 Next.js 应用"。

## Cache Components：把缓存从隐式行为变成组件级声明

Cache Components 是一组特性的总称，核心是 `'use cache'` 指令。可以把 `'use cache'` 理解成组件级别的 Cache-Control HTTP 头：标注了它的组件，其 UI 可以在客户端导航期间缓存在浏览器中，也可以在服务端渲染或构建时提前缓存（[官方发布说明 - Cache Components](https://nextjs.org/blog/next-16-4)）。

```jsx
import { cacheLife } from 'next/cache';

export default async function DashboardPage() {
  const currentUser = await getCurrentUser();

  return (
    <div>
      <p>Welcome, {currentUser.name}</p>

      <Suspense fallback={<Loading />}>
        <Projects userId={currentUser.id} />
      </Suspense>
    </div>
  );
}

async function Projects({ userId }) {
  'use cache';
  cacheLife('hours');

  const projects = await db.query.projects.findMany({
    where: eq(projectsTable.userId, userId),
  });

  return (
    <div>
      {projects.map((project) => (
        <p key={project.id}>{project.name}</p>
      ))}
    </div>
  );
}
```

这些可组合的标注允许在单个页面里混用客户端缓存、可插拔的服务端缓存与请求时渲染，替代了旧版 App Router 的隐式缓存行为。启用该模型需要在 Next.js 配置中同时打开两个开关（[官方发布说明 - Configuration](https://nextjs.org/blog/next-16-4)）：

```js
const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
};

export default nextConfig;
```

Partial Prefetching 最初是独立功能，现在被视为该模型的一部分。16.4 为它补齐了三个新工具。

## 静态保证：ensureStatic 防止动态组件悄悄混入

`'use cache'` 的招牌能力之一，是把静态预渲染内容和请求时渲染内容流式混合在同一次服务端响应里：比如博客正文静态预渲染、当前用户头像请求时渲染。但反过来，对于追求"全静态"的站点，一个误入的动态组件就可能拖累整条路由的性能与成本。

16.4 的 `ensureStatic` 用一行导出语句给出硬性保证（[官方发布说明 - ensureStatic](https://nextjs.org/blog/next-16-4)）：

```js
export const ensureStatic = 'navigation';

export default function Page() {
  return (
    <>
      <UserAvatar /> {/* 动态组件，构建失败 */}
      <Content />
    </>
  );
}
```

- `'navigation'`：最严格，任何动态内容都会让构建失败，保证导航到该路由永远不会在请求时渲染。
- `'prefetch'`：只保证显式预取该路由时获取的是静态内容。
- `'shell'`：保证路由首次被发现时只取静态内容。

`ensureStatic` 也可以加在 layout 上，把保证范围扩展到整个布局下的所有页面；根布局设置 `ensureStatic = 'navigation'` 可以一键保证全站导航静态化。官方指出，电商、营销页和博客这类对成本敏感的站点，这是防止意外请求时渲染的简单手段。

## 分阶段加载：navigation() 与 prefetch()

预取（Prefetch）能消除加载态，但也意味着每个可见链接都会提前拉取整页内容。16.4 提供两个 API 精细控制"什么内容在什么阶段加载"：

- `await navigation()`：把某段缓存内容从预取中排除，延迟到真正导航时才加载。
- `await prefetch()`：把内容从路由 shell 中排除，延迟到显式 `<Link prefetch>` 或 `useRouter().prefetch()` 时才加载。

官方给出的示例是邮件应用：收件箱预取邮件正文时，先只渲染第一条消息，整个线程延迟到用户真正点开时才查询数据库渲染。这类 API 让"急于渲染"和"惰性渲染"的取舍变成组件级决策（[官方发布说明 - navigation/prefetch](https://nextjs.org/blog/next-16-4)）。

## 面向编码智能体的升级工具链

16.4 明显把"用 AI 智能体维护升级"当成一等公民来设计：

- `next upgrade --agent`：检查当前版本、选择目标版本、准备迁移指南、codemod 与验证步骤，让智能体从检查到验证全程完成升级。从旧版本项目运行 `npx next@canary upgrade --agent=latest` 可以拿到最新的升级工具（[官方发布说明 - Agent upgrades](https://nextjs.org/blog/next-16-4)）。
- `experimental.agentUpgrade`：运行 `next dev` 或 `next build` 时自动提示可用升级，策略可选 `'security'`（默认，只提醒已安装版本相关的已知漏洞修复）、`'latest'`（提醒所有新版本）或 `false`（关闭）。
- `experimental.agentFeedback`：编码智能体遇到框架错误或文档不清时，可生成待审查的报告草稿，由人确认后选择是否发送给 Next.js 团队；默认不含源代码、日志、密钥等项目细节，且仅在开启 Telemetry 时生效、不在 CI 中运行。

配套的还有官方 Skills：用于引导智能体采用 Cache Components 与 Partial Prefetching 的迁移指南。升级这件事正在从"人翻文档"变成"智能体执行流程、人做审查"。

## Turbopack 与构建优化：不换配置的体感升级

16.4 里有一批所有应用直接受益的构建优化：

- **磁盘缓存更小**：Turbopack 磁盘缓存占用减少 20–25%，主要数据改用 Zstandard 压缩、元数据仍用 LZ4 保证快速查找，并改进压缩流程以更高效丢弃过期数据（[官方发布说明 - Turbopack cache](https://nextjs.org/blog/next-16-4)）。
- **按需编译服务端更新**：共享服务端模块的变更不再触发已访问页面的后台更新，只有请求需要时才编译应用，减少开发时的无谓后台工作。
- **运行时单 chunk 共享**：Turbopack 运行时合并为跨路由共享的单一 chunk，降低下载体积、提升缓存命中率。
- **更小的生产产物**：生产构建生成更短的 CSS Module 类名，并通过 export mangling 缩短模块间的内部导出名；开发环境保留长类名方便调试（[官方发布说明 - Bundle size](https://nextjs.org/blog/next-16-4)）。
- **可选的实验项**：`turbopackGc` 垃圾回收不再需要的编译缓存；`turbopackLazyDynamicImports` 只在浏览器请求时才编译动态导入的代码；worker threads 让 Babel、PostCSS、webpack loader 在同一进程内运行，减少进程与 socket 通信开销。

## React 19.3 与 React Compiler：编译层的连锁优化

Next.js 16.4 内置 React 19.3：View Transitions 与 Fragment Refs 稳定可用、新增 `browser()` API 与 Trusted Types 支持（[React 19.3 发布说明](https://react.dev/blog/2026/09/09/react-19-3)）。上一版引入的实验性 Rust 版 React Compiler 在 16.4 中进一步加速：新增快速检查跳过无需优化的文件，构建客户端组件时不再重复执行已完成的优化。

Rust 版编译器配合 Turbopack 团队的内存分配改动，**内存占用降低 30%、编译时间减少 15%**（[官方发布说明 - React Compiler](https://nextjs.org/blog/next-16-4)）。启用方式是：

```js
const nextConfig: NextConfig = {
  reactCompiler: true,
  experimental: {
    turbopackRustReactCompiler: true,
  },
};

export default nextConfig;
```

## 对存量项目意味着什么

16.4 给存量项目划出一条清晰的升级路径：先用 `next upgrade --agent` 完成常规版本升级，再通过官方 Skills 逐步采用 Cache Components 与 Partial Prefetching；`ensureStatic` 可以从小范围页面试点，`navigation()` 与 `prefetch()` 用于优化预取成本。旧版的隐式缓存行为被显式声明替代，意味着迁移不是一次开关切换，而是对"哪些内容应该缓存、缓存在哪一层"做一次系统性的显式声明。

从 16.3 的 Instant Navigations、9 月安全版本更新，到 16.4 把 Cache Components 立为默认模型，Next.js 的路线图相当明确：在 Next.js 17 里，这套模型将成为开箱即用的默认。对全栈工程团队来说，尽早理解 `'use cache'` 的语义边界，比等到默认值切换那天再被动适配要省力得多。
