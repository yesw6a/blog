## 一年内，前端工具链换了内核

2026 年是前端工程实践的特殊年份：多年来"靠 JavaScript 工具链维护 JavaScript 代码"的模式被集体改写，两大核心工具分别把内核迁移到原生语言——TypeScript 团队将 `tsc` 用 Go 完整重写，Vite 团队则将打包器统一为 Rust 实现的 Rolldown。

这两件事的共同点是"语义不变、速度量变"：不改变类型检查语义，不破坏插件生态，却在全量构建、编辑器诊断和 CI 时间上给出数量级提升。对工程团队来说，这既是升级红利，也带来一批需要重新评估的迁移决策。

## TypeScript 7.0：tsc 的 Go 重写

2026 年 7 月 8 日，TypeScript 团队正式发布 TypeScript 7.0，官方定位是"10 倍更快的原生移植"（[官方发布说明 - Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)）。新编译器用 Go 编写，保留原代码库的结构与逻辑以保证结果一致，核心变化来自原生代码速度、共享内存多线程和一批新优化。

### 全量构建与内存的实测提升

官方在几个大型开源代码库上对比了 TypeScript 6 与 7 的完整构建时间：

| 代码库 | TypeScript 6 | TypeScript 7 | 提速倍数 |
| ------ | ------------ | ------------ | --------: |
| vscode | 125.7s | 10.6s | 11.9x |
| sentry | 139.8s | 15.7s | 8.9x |
| bluesky | 24.3s | 2.8s | 8.7x |
| playwright | 12.8s | 1.47s | 8.7x |
| tldraw | 11.2s | 1.46s | 7.7x |

内存占用同样下降：vscode 从 5.2GB 降到 4.2GB（-18%），bluesky 从 1.8GB 降到 1.3GB（-26%）。编辑器侧，打开一个带错误的文件到看到首个诊断的时间，在 VS Code 代码库上从约 17.5 秒降到 1.3 秒以内（超过 13 倍）。

大厂反馈也印证了 CI 层面的收益：Slack 把 CI 类型检查从约 7.5 分钟降到 1.25 分钟，合并队列时间减少 40%；Canva 编辑器首错延迟从约 58 秒降到 4.8 秒；Vanta 最大的项目之一获得最高约 9 倍提速。官方还给出稳定性数据：相比 6.0，7.0 语言服务器故障命令减少超过 80%，服务器崩溃减少超过 60%。

### 并行化参数与单线程模式

TypeScript 7.0 把解析、类型检查、产物生成并行化。由于类型检查存在跨文件依赖，官方采用固定数量的 type-checker worker（默认 4 个）并保证相同输入产生相同结果：

```bash
npx tsc --checkers 8
npx tsc --build --builders 4
```

- `--checkers`：控制类型检查 worker 数量，默认 4。`--checkers 8` 时 vscode 构建从 125.7s 降到 7.51s（16.7x）。
- `--builders`：控制 `--build` 下并行项目引用构建数量，对 monorepo 多个项目有帮助，与 `--checkers` 呈乘法关系。
- `--singleThreaded`：完全禁用并行化，适合调试、资源受限环境或与旧版做对比。

调高 worker 通常以内存为代价，CI 机器上反而可能调低。

### 迁移注意：7.0 不带 API，watch 模式重写

TypeScript 7.0 本身不提供编译器 API（官方预期 7.1 引入新 API），依赖程序化访问的工具（如 typescript-eslint）需要与 6.0 并存。官方发布了兼容包 `@typescript/typescript6`，提供名为 `tsc6` 的可执行文件，并支持通过 npm alias 让两个版本共存：

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}
```

此外，`--watch` 模式被完整重写，底层改用 Parcel 的文件监听器，跨平台稳定性更可靠。工具链中凡是直接 import `typescript` API 的环节，都需要在升级前核对兼容包或等待 7.1。

## Vite 8：Rolldown 统一开发与生产打包

2026 年 3 月，Vite 8 正式发布（[官方发布说明 - Vite 8.0](https://cn.vite.dev/blog/announcing-vite8)）。官方称这是"自 Vite 2 以来最重要的架构变化"：Vite 8 用 Rolldown 作为**单一、统一、基于 Rust 的打包工具**，取代此前开发期用 esbuild、生产构建用 Rollup 的双引擎方案，宣称构建速度可达 10 到 30 倍，同时保持完整的插件兼容性。

此前 Vite 采用双引擎是务实选择：esbuild 负责开发期的快速转译与依赖预打包，Rollup 依靠丰富插件 API 支撑生产构建生态。代价是 dev 与 prod 语义存在细微差异，且维护两套工具链。Rolldown 用 Rust 内核 + Rollup 兼容 API + esbuild 量级的速度解决这个问题，解析器、模块解析、sourcemap 由同属 VoidZero 的 Oxc 团队提供。

### 官方与实测的性能数据

- Vite 官方博客称 Rolldown 比 Rollup 快 10 到 30 倍（大型模块图项目显著，小项目绝对提升有限）。
- 预览期（rolldown-vite）第三方实测：Ramp 生产构建时间下降 57%，Beehiiv 下降 64%，Mercedes-Benz.io 下降 38%。
- Vite 8 发布时周下载量 6500 万次，并上线 `registry.vite.dev` 插件目录，每日从 npm 收集 Vite、Rolldown 与 Rollup 插件数据。
- 发布门槛：Vite 8 要求 Node.js 20 及以上；安装体积因 Rolldown 与 lightningcss 原生二进制增加约 15MB。

### 生态连锁反应

Vite 8 的架构变化迅速传导到周边生态：

- **@vitejs/plugin-react v6 改为基于 Oxc**，不再依赖 Babel 转译链（相关依赖从约 45MB 降到约 8MB）。
- **SvelteKit 3.0**（2026 年 10 月 1 日发布）将配置迁入 `vite.config.ts`，并要求 Vite 8、TypeScript 6 与 Node 22.17。
- **Astro 7** 内部使用 Vite 8 + Rolldown。
- **Rolldown 1.0** 于 2026 年 5 月 7 日发布，此后以约 11 天一个版本的节奏迭代到 1.2.x，npm 周下载量突破 1.3 亿次。

治理层面，2026 年 6 月 Cloudflare 收购了 VoidZero（Vite / Vitest / Rolldown / Oxc 背后的公司），并承诺保持 MIT 开源、出资 100 万美元设立 Vite 生态基金。选型时，工具维护主体的激励结构也进入了团队的评估清单。

### 迁移建议

社区给出的稳妥路径是先小步切换、再升级主版本：在 Vite 7 上先改用 `rolldown-vite` 包验证业务代码兼容性，解决 Rolldown 特有差异后，再升级到 Vite 8。`rollupOptions` 大多可原样工作，esbuild/Rollup 配置有自动转换层。对自定义 Babel 插件（如 styled-components 相关）需要找 Oxc/Vite 插件等价物，不能默认继续使用 Babel。

## 趋势：类型检查与运行时解耦、原生工具成为默认

与 TypeScript 7.0、Vite 8 平行的是 Node.js 的 type stripping：原生类型剥离在 24.12.0 与 25.2.0 中稳定，并从 v22.18.0 起默认启用。Node 直接运行带类型的文件、TypeScript 7 负责类型检查，两个关注点从此分离。对于不含参数属性等需要代码生成语法的项目，甚至可以在构建阶段省掉 `tsc` 产物生成。

把三条线放在一起看，2026 年的工具链原生化不是孤立的框架升级，而是一次协同换代：

- 语言层：TypeScript 编译器换到 Go，多核并行成为默认收益。
- 构建层：Vite 系列换到 Rust，dev 与 prod 语义统一。
- 运行层：Node 原生剥离类型，类型系统与执行分离。

对普通业务团队，最直接的影响是本地反馈循环与 CI 时间显著缩短，但迁移前要重点核对三件事：依赖编译器 API 的工具（typescript-eslint 等）是否已适配、自定义 Babel/PostCSS 插件是否有原生等价物、以及 monorepo 并行构建参数是否匹配 CI 机器资源。原生工具链把"等待"省了下来，剩下的工程判断——迁移节奏、插件替换、并行度调优——才是这一轮升级真正考验团队的地方。
