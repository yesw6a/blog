后量子密码学的讨论很容易停留在"量子计算机还有多少年"。但工程上真正推动迁移的，是一个不需要等到那一天的威胁模型：录下来的流量会在未来被解密。

这类攻击不要求攻击者今天有能力解密，只要求它今天有能力存储。TLS 1.3 的会话密钥由握手阶段的密钥交换决定，一旦这段握手用的是纯经典算法，那么今天抓到的密文在未来具备密码学相关量子计算机之后，仍然可以被回溯恢复。这就是所谓 harvest now, decrypt later。

这个模型决定了迁移顺序：密钥交换优先，签名靠后。签名的伪造威胁是实时性的——攻击者必须在连接发生时就能伪造证书，而那时量子计算机是否存在才是关键；密钥交换的威胁则是回溯性的，今天录下的每一个字节都算数。理解了这个不对称，接下来的一切取舍才有意义。

## 一、ML-KEM 不是"加密算法"，是共享密钥的生成器

[X25519MLKEM768](https://www.rfc-editor.org/rfc/rfc10024) 里那个 ML-KEM，标准定义在 [NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)，2024 年 8 月 13 日发布，正式名称是 Module-Lattice-Based Key-Encapsulation Mechanism。它的安全性建立在 Module Learning with Errors 问题的计算困难性上，与整数分解、离散对数这一族假设没有关系——这也正是它能躲开 Shor 算法的原因。

关键在于它被定义为 KEM（密钥封装机制），而不是密钥交换协议。FIPS 203 给出的是一组三段式接口：

```text
KeyGen()            -> (pk, sk)      生成公私钥对
Encaps(pk)          -> (ct, ss)      用公钥产出密文与共享密钥
Decaps(sk, ct)      -> ss            用私钥从密文恢复共享密钥
```

注意这套接口和 ECDH 的形态不一样。ECDH 里双方各出一个公钥，各自算出同一个共享值；KEM 里只有一方持私钥，另一方用公钥"封装"出一个密文，双方得到同一个共享密钥。所以 ML-KEM 单独并不能完成一次双向密钥协商，它天然需要和别的东西组合——这一点直接决定了后面所有字节数的来源。

FIPS 203 定义了三个参数集，按安全强度和性能反向排列：ML-KEM-512、ML-KEM-768、ML-KEM-1024。TLS 里被大规模部署的 X25519MLKEM768 用的是中间那档，ML-KEM-768。

还有一个常见误解需要顺手澄清：ML-KEM 不负责保护网页内容。它只产出一个共享密钥，后续的对称加密仍然由 AES-GCM 或 ChaCha20-Poly1305 完成。对称密码在足够密钥长度下并不被 Shor 算法实质威胁，这也是为什么整个迁移的重心落在密钥建立这一步，而不是批量加密。

## 二、混合是拼接，不是新算法

混合密钥交换的框架规范是 [RFC 9954](https://www.rfc-editor.org/rfc/rfc9954)（Informational，2026 年 7 月）。它的核心构造比名字听起来朴素：定义一个全新的 NamedGroup，让它的 key share 就是两个组件 share 的拼接，让它的共享密钥就是两个组件共享密钥的拼接。

拼接之后，这个结果替换掉 TLS 1.3 密钥调度中原本由 (EC)DHE 提供的那一份输入，其余流程完全不动。规范没有引入新的协商机制，也不改 Handshake Secret 的推导步骤。

这种设计带来一个很好用的安全性质：只要两个组件中有一个还站得住，会话密钥就还站得住。X25519 被未来的量子计算机攻破，还有 ML-KEM；ML-KEM 被经典密码分析找到结构性弱点，还有 X25519。这是一个明确的过渡期对冲，而不是临时补丁。

代价也很直接：共享密钥从 X25519 的 32 字节变成 64 字节，而且全部长度必须在协商时就确定，不能带变长编码。这些约束写在规范里，也写进了每个实现的缓冲区大小里。

## 三、字节账：这 1.2 KB 花在哪

[RFC 10024](https://www.rfc-editor.org/rfc/rfc10024)（标准跟踪，2026 年 8 月）给出了三个具体组的参数。把所有数字摊开，账单就清楚了：

| NamedGroup | 码点 | 客户端 key_share | 服务端 key_share | 共享密钥 |
| ---- | ---- | ---- | ---- | ---- |
| X25519（经典） | 0x001D | 32 B | 32 B | 32 B |
| X25519MLKEM768 | 0x11EC（4588） | 1,216 B | 1,120 B | 64 B |
| SecP256r1MLKEM768 | 0x11EB（4587） | 1,249 B | 1,153 B | 64 B |
| SecP384r1MLKEM1024 | 0x11ED（4589） | 1,665 B | 1,665 B | 80 B |

X25519MLKEM768 的客户端 share 是 1,184 字节的 ML-KEM-768 封装公钥加上 32 字节的 X25519 公钥；服务端回的是 1,088 字节的 ML-KEM 密文加上它自己的 32 字节 X25519 share。和纯 X25519 的 32 字节相比，客户端这一侧膨胀了 38 倍。

这里有个容易踩的坑：组名叫 X25519MLKEM768，但实际拼接顺序是把 ML-KEM 放在前面、X25519 放在后面。RFC 10024 专门说明了这点——命名没有遵循 RFC 9954 第 3.2 节的顺序约定，属于历史遗留，实现必须按实际协商顺序处理，不能按名字猜。

把视角从字段级抬到握手级：一次首次连接，客户端大约多送出 1.2 KB，服务端大约多回 1.1 KB。在一个通常只有几百字节的 ClientHello 上，这是一次结构性变化——不是多了几个扩展，而是把整个消息推过了一个沿用多年的尺寸阈值。

## 四、真正的故障点不是 CPU，是中间盒

密码学运算本身在当代硬件上并不构成瓶颈，问题出在别的地方。

[tldr.fail](https://tldr.fail/) 这个项目专门收集这类失败样本，它描述的现象很具体：后量子 ClientHello 明显大于经典 ClientHello，超过单个数据包能承载的阈值；而一部分服务器在读取 ClientHello 时，假设自己调用一次 TCP read() 就能拿到完整消息。消息一旦跨包，它就只读到前半截。

这个 bug 在经典密码学下其实也存在，只是极少被触发——经典 ClientHello 通常一个包装得下。后量子的 1.2 KB 把这个沉睡多年的假设直接叫醒了。

失败形态还分几种，工程上要分开处理：

- **直接重置连接**：设备读到不完整的长度字段或看到不认识的组码点，干脆断开。
- **静默退回经典**：服务端忽略 hybrid 组，另选一个双方都支持的经典曲线，连接成功但后量子保护消失，日志里看不到任何异常。
- **二次往返**：客户端首次猜错 key share，服务端发出 HelloRetryRequest，握手多一个往返。这对高频短连接的影响远大于对长连接的影响。

第三种情况最容易被忽略，因为它是"正确实现"下的正常行为——TLS 1.3 允许 HelloRetryRequest，只是每次多付一个 RTT。在 CDN 回源的场景里，这个往返恰好落在最容易放大延迟的一跳上。

还有一个必须点明的边界：如果链路上存在解密型 TLS 检查设备，它会分别与客户端和服务器各建一条连接。那么"客户端这一侧是后量子"完全不能推导出"服务端那一侧也是后量子"。两段链路要分别验证，这一点在做合规审计时尤其重要。

## 五、三个采用率数字，不能相加也不能互相替代

翻 Cloudflare 公布的数据，很容易看到几个相差很大的百分比。它们测的其实是同一条连接上三个不同的升级动作。

[2026 年 2 月 27 日的 Radar 公告](https://blog.cloudflare.com/radar-origin-pq-key-transparency-aspa/)给出了客户端与源站两端的对照：客户端对后量子加密的支持率从 2024 年初的不到 3%，涨到 2026 年 2 月的超过 60%；而同一时间点，支持 X25519MLKEM768 的源站约为 10%，2025 年初这个数字还不到 1%——一年多时间涨了十倍。

[2026 年 4 月 7 日的路线图公告](https://blog.cloudflare.com/post-quantum-roadmap)则从另一个视角给出网络整体水平：人类流量中超过 65% 已经是后量子加密，并把 2029 年设为全产品线（含认证）实现后量子安全的目标年份。

| 观察视角 | 衡量的是什么 | 公开数字 | 时点 |
| ---- | ---- | ---- | ---- |
| 浏览器支持率 | 客户端是否愿意协商 hybrid | 从不到 3% 到超过 60% | 2024 初 → 2026-02 |
| 网络人类流量 | 端到端实际协商成功的比例 | 超过 65% | 2026-04 |
| 源站支持率 | 客户自有服务器是否支持该组 | 从不到 1% 到约 10% | 2025 初 → 2026-02 |

这三个数字的落差说明了一件事：浏览器这一端基本已经就位，因为一次浏览器发版就能覆盖大量用户；源站这一端慢得多，因为它散落在无数套不同年代、不同供应商的 TLS 终止设备上，每一台都要单独升级、单独验证。所谓"后量子迁移完成度"，在没有指明是哪一段链路之前，基本没有信息量。

## 六、还有一半没迁：认证

上面所有字节账算的都是密钥建立。而 HTTPS 同时做两件事：保密，以及证明你连的是真的那个站点。后者靠证书和签名，与密钥交换是两套东西。

迁完密钥交换，并不代表这套连接已经是后量子安全的。当前浏览器用 X25519MLKEM768 连上一个站点时，会话密钥是后量子安全的，但用来认证这次握手的服务器证书，绝大多数仍然由 ECDSA P-256 或 RSA-2048 签发。这个"一半新一半旧"的状态，是现阶段部署最本质的特征。

原因前面已经提过：伪造签名必须在连接发生的那一刻就能做到，不存在回溯风险；而业界同时还要承担另一笔账——后量子签名的体积。ML-DSA 的公钥与签名都在 KB 量级，塞进证书链之后，握手会再涨一轮，而这轮增长动的是 X.509 信任链、中间 CA 轮换和各家根证书库的审核周期，这些环节的节奏以年计，不是升级一个库版本能解决的。

所以正确的判断是：不要现在就去采购所谓"后量子证书"，那部分生态还在成形；今天能拿到的确定性收益，是把密钥交换这一半迁完。

## 七、工程侧的可执行检查

如果要判断自己这套链路到底迁到哪一步，动作其实不多，但每一件都要落在具体链路上。

**先确认协商结果，而不是配置项。** 配置里写了组名不等于握手里真的用上了。服务端配置如果是基于旧版 OpenSSL 编译的，遇到不认识的组名通常会静默忽略——配置加载成功，行为毫无变化，这是最典型的"看起来做了"。

```bash
# OpenSSL 3.5 及以上，显式指定组名发起一次 TLS 1.3 握手
openssl s_client -connect example.com:443 -tls1_3 \
  -groups X25519MLKEM768 -brief
```

返回里能看到实际协商的组名，才算验证完成。浏览器一侧可以看开发者工具 Security 面板里的密钥交换项。

**审计所有终止或检查 TLS 的设备。** 负载均衡、WAF、透明代理、老式防火墙，任何一处只读首段 ClientHello 的设备都可能成为断点。中间盒的问题不会只在浏览器上暴露，业务侧的 SDK、脚本、伙伴系统同样会撞上。

**分开验证每条链路。** CDN 到浏览器是一段，CDN 到源站是另一段。前者大概率已经是 hybrid，后者往往还是纯经典——而这恰好是承载真实数据的那一段。

**把回退当成短期手段。** 浏览器厂商提供的关闭后量子组的开关，定位是过渡期的排障工具，不是长期兼容方案。把它当默认配置写进基线，等于在迁移账上留了一笔永远还不清的债。

## 八、小结

X25519MLKEM768 值得作为一个样本看。它是目前互联网上部署规模最大的后量子密码学应用，而它成功的原因并不神秘：混合构造让它在密码学上足够保守，标准路径清晰（FIPS 203 定义算法，RFC 9954 定义拼接，RFC 10024 定义具名组），代价可以被量化——1,216 字节的 key_share，1,120 字节的回应，外加一次可能被触发的额外往返。

真正卡住迁移的从来不是数学，而是十多年前写下的那些"一个包肯定装得下"的假设。这些问题在纯经典环境下永远不会显现，只有在握手消息被推过阈值的那一天，才会集体浮出水面。下一个要面对的，是证书链上以 KB 计的后量子签名——同样的剧本，更大的数字。
