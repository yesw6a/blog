11 月 17 日到 18 日这四十八小时里，出现了三份性质完全不同的材料，测的却是同一件事：榜单分数的增长，有没有变成真正完成的工作。

- 一份 arXiv 预印本借美国出口管制造成的 19 天模型断供，做了一次罕见的自然实验（[arXiv:2611.23216](https://arxiv.org/abs/2611.23216)，2026 年 11 月 17 日提交）。
- Epoch AI 用自己内部的真实工作当考题，六个前沿模型没有一个是他们愿意按员工标准接受的（[Epoch Automation Reports](https://epoch.ai/benchmarks/epoch-automation-reports)）。
- Runta 不测模型，测包裹模型的 harness：同样一批终端任务，每通过一次的成本从 1.05 美元到 18.34 美元（[FrontierHarness Eval](https://runta.com/blog/introducing-frontierharness-eval)）。

三份材料的证据强度各不相同，但结论方向一致，而且共同指向一个被长期省略的环节：**验收**。评测把"生成了看起来对的输出"当作完成，生产环境要的是"有人愿意接受这份交付物"。这两者之间的落差，就是本文想量化的东西。

## 一、19 天断供：唯一换了模型、没换人的自然实验

模型升级对生产力的真实影响很难测，因为换模型的人往往同时在做别的事。这篇预印本找到了一个干净的切面。

2026 年 6 月 12 日，一道美国出口管制指令使 Claude Fable 5 的访问被切断 19 天。断供把人和项目钉在原地，只有模型变了：大部分原 Fable 5 用户回退到 Opus 4.8，而在 SWE-Bench Pro 上 Opus 4.8 比 Fable 5 低 11 分——按常规理解，这是明确的能力降级。

作者追踪了 297 名 Fable 5 用户在断供前、中、后的 GitHub 拉取请求，并以 8,908 名全程停留在 Opus 4.8 的开发者作为对照组，用带开发者与日期固定效应的双重差分模型估计效应。随后又把同样的比较在 2026 年另外五次模型升级前后重做了一遍（1,208 名开发者、15,442 个拉取请求）。

结果：

| 指标 | 估计值 | 95% 区间 | 结论 |
| ---- | ---- | ---- | ---- |
| 断供期拥有 Fable 5 对 7 日 PR 合并率的影响 | +1.4 个百分点 | [-1.4, +4.3] | 不显著 |
| 五次升级的加权平均合并率效应 | -0.9 个百分点 | [-1.9, +0.2] | 不显著，五次估计全为负 |
| 每周合并 PR 数量变化 | +2.4% | [-4.9%, +10.2%] | 不显著 |

**一个在专业基准上高 11 分的模型，没有在真实合并率上留下可测痕迹。** 更值得注意的是那五次升级：估计值全为负，加权均值略低于零。作者没有把这解释成"更好的模型有害"，合理的读法是——在已经成型的开发流程里，模型能力不是决定产出的一道硬约束，代码审查、需求澄清、协作等待这些环节把差异吸收掉了。

要提醒的是，这是预印本，尚未经过复现和同行评审。合并率也不是生产力的全部，它可能低估了模型在"少走弯路"上的价值。但作为自然实验，它的设计比大多数厂商自测更接近因果推断。

## 二、Epoch：六个前沿模型，没有一个过员工线

Epoch AI 的做法更朴素：把自家日常要做的工作当考卷。任务来自他们内部真实的生产需求，分为平面设计、数据洞察生成、AI 数据中心研究、研究课题四类。每个模型跑在它对应的原生 harness 上、取最高推理档，并且**关闭记忆与技能写入**，避免一个任务上学到的东西带到下一个任务。最终由人工按内部 rubric 打分。

这些任务的形态本身就值得看：AI 数据中心研究要查卫星影像（SkyWatch）、读写表格（Airtable）、分析图片（QGIS）、用浏览器核对，预测在真实世界里经常要等 48 小时才有影像返回；研究任务则给一笔固定预算（OpenRouter 上 500 美元额度）让模型自己设计并执行实验。

公开整理的结果是：**六个前沿模型里没有一个达到了 Epoch 对员工提交所要求的标准。** 有意思的是分数之间的缝隙——Fable 5.2 与 GPT-6.2 Astra 在 Epoch 的能力指数上并列 174 分，但落到这些真实任务的平均完成度，前者 82%、后者 65%，相差 17 个百分点。而在结构化的数据中心研究任务上，Fable 5.2 拿到 97.5%、Opus 5.5 拿到 87.5%，其中 Opus 5.5 用了不到 3 小时，对标的外包人员约需 16 小时（上述具体分数来自第三方对 Epoch 报告的整理）。

同一份整理里还留着两个更锋利的观察：所有模型在"发明新棋类变体"这项任务上都只是复用已有的变体，没有给出真正分布外的设计；除一个例外，模型都认为自己的输出优于人类金标准。**自我评价的校准偏差，正好抹平了"我看它做得不错"这种直觉判断的可靠性。**

Epoch 自己在页面上把局限写得很清楚：任务集很小、每个模型每个任务只跑一次、评分含主观成分、任务是 Epoch 特有的、不同 harness 会带来额外的不公平。这些限制让单个分数不宜当作结论；但"没有一个达标"这个方向性判断，恰恰是他们认为比具体数字更可靠的部分。

## 三、Runta：同一批任务，每通过一次差 17 倍

第三份材料干脆不测模型能力，测包裹模型的那层软件。

Runta 与 Baseten 合作的 FrontierHarness Eval v1.0 用了 30 个任务（21 个来自 Terminal-Bench、9 个来自 DeepSWE），9 种 harness、12 种配置、共 360 次评测，全部用确定性验证器判分。为了保证可比，他们把每个 harness 与任务环境的组合安装一次后固化成"金版检查点"，360 次评测都从同一检查点恢复——相同的 vCPU、内存、磁盘大小和**内存状态**，不继承上一次运行留下的文件系统漂移或热页缓存。模型统一用 Kimi K3，避免让 Claude 或 GPT 在自己家的 harness 上占主场。

结果最刺眼的不是通过率，而是成本：

| 配置 | 每通过一次成本 | 通过率 | token 加权缓存命中 |
| ---- | ---- | ---- | ---- |
| Codex | $3.47 | 66.7% | 88.0% |
| DSH Creator | $3.28 | 63.3% | 84.3% |
| Claude Code | $18.34 | 63.3% | 67.8%（加权仅 25.0%） |
| Pi | $2.43 | 60.0% | 79.4% |
| Exo Harness | $1.05 | 53.3% | 70.3% |
| OpenCode | $3.24 | 50.0% | 78.4% |

12 种配置的通过率挤在 50.0% 到 66.7% 之间，只有 17 个百分点的差距；每通过成本却横跨 1.05 到 18.34 美元，约 17 倍。**能力差不多，账单差一个数量级。**

Runta 给出的三个解释都跟验收有关。第一，"完成任务"和"便宜地完成任务"是两种独立技能：Claude Code 与 DSH Creator 通过的任务数一样多，每通过一次的成本却差 5.6 倍。第二，缓存命中率不等于成本：一个缓存命中率很高的 300 步失败轨迹，照样比一次短促的缓存未命中更烧钱，**你付的是步数和 token，缓存只改单价**。第三，最便宜的 Exo Harness 之所以便宜，是因为它更早收手——最难的那个任务上它花 1.46 美元就失败退出，其他配置要花 5.97 美元。

第三点把问题挑明了：**在 agent 经济性里，失败也是要计价的产品。** 该评测的后续版本 v1.1 扩到 22 种配置、5 个模型、62 个任务，据公开解读，失败与超时的运行吃掉了约 64.5% 的推理花费，而模型本身解释了约 92.8% 的成本方差，固定模型后 harness 之间仍能拉开 1.8 到 5 倍的差距。

## 四、脱钩发生在哪一步

把三份材料叠起来，脱钩的机制其实很具体。

**第一，评测的结算单位是片段，生产的结算单位是交付。** 基准题通常给出一段可自动判定的输出，判分器看的是这段输出对不对。而真实工作里，"对不对"只是第一关，"能不能被下一个环节接受"才是终点。SWE-Bench 这类合并导向的基准已经算贴近现实了，而那份自然实验恰恰说明：即便在合并率这个相当贴近的口径上，11 分的榜单差也测不出来。

**第二，长程任务的误差是累积的，而榜单是单点的。** 一次数据中心的调研要跨几十上百个步骤，中间一个 API 返回的图片尺寸过大就会中断；Epoch 提到这类失败经常需要人介入重开 session 并指回上一次的轨迹。榜单不会惩罚"第 47 步忘了自己在干什么"，生产会。

**第三，没有验收门，花费就会流向失败。** Runta 的 17 倍成本差和 v1.1 里失败的多数花费，本质上是同一件事：系统在没有"完成定义"的情况下持续调用工具，直到耗尽预算或超时。这也解释了为什么 Epoch 里模型会偏好自己的输出——如果验收标准由模型自己给出，它当然会给自己判过。

## 五、可以改的四个口径

如果接受上面的诊断，落地动作并不复杂，难的是愿不愿意把评测从"选型"变成"运维"的一部分。

**把验收脚本当成一等公民。** 与其争论模型分数，不如先写清"什么叫做完了"：一个可执行的 acceptance 脚本、一份可核查的 checklist、或者一段必须通过的回归。Runta 的结论在这里反过来用最有价值——它的成本差异主要由 harness 与模型的配对决定，而验收门是这套配对里唯一能硬性截断花费的部件。

**用"每通过一次的成本"做预算单位。** token 单价是采购口径，每通过成本才是产研口径。按 Runta 的表，把单价降 20% 可能被失败率上升完全吃掉；反过来，一个贵 3 倍但通过率高的配置，可能每通过成本更低。做容量规划时按这个数走，才不会在月底被账单教育。

**给失败设价格上限。** 既然失败也是产品，就要有止损：最大步数、最大工具调用数、最大墙钟时间，三者取先到者。Exo Harness 的 1.46 美元失败不是缺陷，是可重试性的前提——失败得便宜，才敢重试。

**用内部任务建自己的 rubric。** Epoch 的方法论里最值得抄的不是分数，而是那几条设计约束：任务来自真实生产需求、给足和人类外包同等的信息、关闭跨任务记忆、按内部质量标准人工打分、并且承认样本小和评分主观。这套东西不需要六个前沿模型，只要你自己团队的十来个端到端任务，就足以判断一次升级到底有没有用。

## 六、边界与不确定

三份材料的可信度不同，不该等量齐观。

那份自然实验是预印本，未复现，合并率也只是生产力的代理指标，作者自己也只主张"未观测到显著提升"。Epoch 的任务集规模有限、每任务单次运行、评分含主观判断，官方明确说具体数值不宜当基准真值。Runta 只覆盖软件开发与终端类任务，初版只用一个模型、每配置每任务跑一次，且没有测重试策略的影响。

更要紧的一条：**这三份材料都在说"高分不等于多干活"，而不是"模型能力不重要"。** 在单点、可自动验证、上下文短的任务上，能力差异依然直接对应产出差异。真正被证伪的是那种默认假设——榜单涨了，团队产出就会跟着涨，不需要改流程，不需要加验收。

这个默认假设之所以危险，是因为它同时取消了改进的方向。如果涨分就能涨产出，那剩下的工作只有等新模型；而实际上，验收门、失败预算、每通过成本这些今天就能改的东西，可能比下一代模型更早带来收益。
