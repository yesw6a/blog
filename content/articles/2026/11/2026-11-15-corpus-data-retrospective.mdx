## 口径先说清楚，否则数字没意义

| 项目 | 这次采用的口径 |
| --- | --- |
| 统计对象 | `content/articles` 下递归扫描到的全部 `.mdx` |
| 已发布 | Frontmatter 里 `draft: false` |
| 字符数 | 去掉 frontmatter 后的正文长度，含 Markdown 标记，不是字数 |

需要说明的是字符数这一项：它把标题符号、链接 URL、代码块里的内容都算了进去，所以它只能用来横向比较哪几类偏长偏短，不能当成真实字数读。真正精确的字数需要另一套分词，那是另一个话题。

另外，这次一共扫到 104 个文件，104 个都是 `draft: false`。也就是说，此刻没有任何一篇草稿躺在仓库里——这个数字本身也是结论的一部分。

复现只需要一个脚本，放在仓库外面跑，不写入任何被跟踪的目录：

```js
// node stats.mjs D:/workspace/blog/content/articles
import fs from 'node:fs';
import path from 'node:path';

const root = process.argv[2];
const files = [];
(function walk(dir) {
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name);
    e.isDirectory() ? walk(p) : p.endsWith('.mdx') && files.push(p);
  }
})(root);

const fm = files.map((f) => {
  const raw = fs.readFileSync(f, 'utf8');
  const cut = raw.indexOf('\n---', 3);
  const head = raw.slice(0, cut);
  const get = (k) => (head.match(new RegExp(`^${k}:[ \t]*(.*)`, 'm')) || [, ''])[1].trim();
  return { cat: get('category'), date: get('publishedAt'), draft: get('draft'), chars: raw.slice(cut + 4).length };
}).filter((a) => a.draft === 'false');

const count = (arr, fn) => arr.reduce((m, x) => ({ ...m, [fn(x)]: (m[fn(x)] || 0) + 1 }), {});
console.log(count(fm, (a) => a.date.slice(0, 7)));
console.log(count(fm, (a) => a.cat));
```

随笔写多，其实有机制上的原因：它不需要一手素材。一篇 T2 工程实践要跑通构建、拿到可对比的数据、再把结论写清楚；一篇随笔只要有想法就能落笔。素材成本低的分类，长期一定超配。这不是意志力问题，是成本结构问题。

`AIGC` 出现 104 次这一点，说明标签系统实际上兼任了合规标识。按 `docs/article-writing-rules.md` 的规则，AI 参与写作的文章必须三项齐全：标签里有 `AIGC`、Frontmatter 有 `AIGC` 元数据、正文末尾有可见声明。标签在这里不是分类工具，是审计凭据。它也就不该被当成「标签质量」问题来讨论。

真正的问题在 162 个一次性标签。按 `docs/article-content-architecture.md`，每个标签值都会生成静态标签页 `/articles/tag/[tag]`；平均每篇 5.5 个标签，意味着一篇文章落地就带来五六个新页面，其中多数页面上只有这一篇。

这算不上错误，但它是标准的「关键词当标签用」。标签的价值在于聚类——点进去能看到同类的一组文章。一个只有一篇文章的标签页，读者点进去只会原路返回。

我倾向的改法是：新文章优先复用已有的高频标签，只有确认后面还会再写两篇以上时，才引入新标签。这条规则比「控制标签总数」更可执行，因为它判断的是未来而不是过去。

## 归档结构：下一个压力点在 111 篇

104 篇按每页 10 篇切分，现在是 11 页，最后一页 4 篇。再发 7 篇、总数到 111 篇时，才会出现第 12 页。

按 `docs/article-content-architecture.md` 的设计，这是编号分页的固有行为：每新增一篇文章，倒序分页的内容整体后移一位，页面总数随之增长。构建期生成，不需要手工维护，但每次发布引起的页面位移量会越来越大。

另一个容易被忽略的边界是 RSS。订阅源只输出最新 50 篇，而站内已公开 104 篇——**54 篇已经不在 RSS 里了**。这不是 bug，是刻意的防膨胀设计；但它意味着「发过就等于被订阅者看到」这个假设只对最近 50 篇成立。老文章要重新被读到，只能靠站内标签、搜索和外部链接。

文档里已经列为后续可能的方案是增加 `/articles/YYYY/MM` 月份归档，给深层内容一个不随新文发布而位移的入口。以现在 11 页、104 篇的规模还不急，但如果明年保持这个节奏，五个月又会多出上百篇，那时候月份归档会从「可选项」变成「必要项」。

## 这轮复盘要落成的四条改动

1. **T6 本周期剩余额度不再动用**。下一篇回到 T1 或 T2，把 22.1% 的累计占比往下压一点。
2. **给 T2 建素材清单**。仓库的构建脚本、内容检查、静态分页、搜索索引都是现成的一手素材，先把这些写掉，再谈外部选题。
3. **标签复用优先**。新文章先看已有 230 个标签能不能覆盖，只有确认未来至少还有两篇同主题时才新增。
4. **随笔也要标来源**。凡是出现具体数字，给出可以点开的入口或者说明数据来自本地哪次统计，而不是留在「我之前跑过」的印象里。

至于权重本身，我不打算现在就改。偏差是累计口径算出来的，而规则要求看最近 28 天——近 28 天里 T6 是 19.0%，T2 是 9.5%，方向一致但幅度小得多。先按上面四条执行一个周期，下一轮复盘再看要不要动权重表。
