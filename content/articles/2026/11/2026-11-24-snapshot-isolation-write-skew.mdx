隔离级别这件事，多数人是从一张四行五列的表里学会的。表上写着脏读、不可重复读、幻读三列，四行分别是四个级别，勾勾叉叉排得整整齐齐，看起来是个可以被背诵下来的规格说明。

问题在于那些叉号只覆盖了一部分真相。SQL 标准是用"禁止哪些现象"来定义隔离级别的，而"现象"这个词的范围，取决于标准制定时研究者已经能形式化描述多少东西。标准之前加进去的现象，被写成了检查项；标准之后被人发现的异常，只能落在表格外面。

写偏斜就在表格外面。它不需要脏读，不需要不可重复读，也不需要幻读，却能让两个事务的结果拼出一个任何串行顺序都无法产生的状态。而 PostgreSQL 的 REPEATABLE READ 恰好就是那个"挡住了表里所有现象、却挡不住它"的级别。

## 一、先看那张表缺了什么

按 [PostgreSQL 官方文档 13.2 节](https://www.postgresql.org/docs/current/transaction-iso.html) 的表述，标准给出的现象有四类：脏读、不可重复读、幻读，以及序列化异常（serialization anomaly）。前三类是行级别的——你读到别人没提交的数据、你两次读到不同的值、你的范围查询第二次多出了行。第四类才是真正抽象的：一组并发事务的执行结果，不存在任何与之等价的串行顺序。

PostgreSQL 在这张表上做了一个容易被忽略的偏离：它内部只实现三个隔离级别，请求 `READ UNCOMMITTED` 会被当成 `READ COMMITTED` 处理。文档给出的理由是，把标准的四个级别映射到它的多版本并发控制架构上，这是唯一说得通的做法。换句话说，这个数据库里根本不存在"能读到未提交数据"的路径——视图永远来自某个已提交的快照。

第二个偏离出现在 REPEATABLE READ 那一行。标准对这个级别只要求禁止脏读和不可重复读，幻读是可以发生的；PostgreSQL 不允许幻读，文档明确说这是标准允许的越界，因为标准规定的是最低保护，更高的保证不算违规。

于是 REPEATABLE READ 在 PostgreSQL 里变成这样：标准表 13.1 中列出的所有现象它都禁止，唯独序列化异常除外。

这一行就是裂缝所在。"除序列化异常之外全部禁止"听起来已经很接近可串行化了，但序列化异常不是一种边角情况，它是一个范畴——所有那些"每一行看起来都合法、拼起来却不合法"的异常都装在这里面，写偏斜是其中最朴素的一个。

## 二、REPEATABLE READ 的真名

文档里有一句话值得单独拎出来：这个隔离级别用的技术，在学术文献和部分其他数据库产品里叫 **Snapshot Isolation**（快照隔离）。

差别来自快照的取法。READ COMMITTED 下，每条语句开始的那一刻取一次快照，所以同一事务里两条 `SELECT` 完全可能看到不同的数据；REPEATABLE READ 下，快照在事务内第一条非事务控制语句开始时取定，之后整个事务看到的是一个完全稳定的视图。文档还补了一句常被跳过的说明：这种稳定视图不必然等价于某个串行执行，并给了一个具体场景——只读事务可能看到控制记录已标记"批次完成"，却看不到逻辑上属于该批次的一条明细，因为它读的是控制记录的旧版本。

还有一段历史：在 9.1 之前，请求 `SERIALIZABLE` 得到的行为，就是今天 `REPEATABLE READ` 的行为。想要旧语义的人，现在应该显式要 REPEATABLE READ。这句话反过来读更有信息量：真正的可串行化是 9.1 才有的东西，之前那个名字只是一张标签。

名字与语义的错位有实际后果。别的系统里 REPEATABLE READ 和 Snapshot Isolation 可能是两个行为不同的级别，把应用从 A 数据库搬到 PostgreSQL，配置项名字对上了，语义不一定对上。文档在这里引了 Berenson 等人 1995 年那篇批评 ANSI SQL 隔离级别的文章，作为"这两个技术之间的差异直到标准制定之后才被形式化"的出处——也就是说，表格的定义早于人们对表格的理解。

## 三、写偏斜：冲突发生在读集与写集的交叠处

官方文档给的例子很小，但它精确。

```sql
CREATE TABLE mytab (class int NOT NULL, value int NOT NULL);
INSERT INTO mytab VALUES (1, 10), (1, 20), (2, 100), (2, 200);
```

事务 A 算出 `class = 1` 的总和是 30，把它作为一行写进 `class = 2`；事务 B 同时算出 `class = 2` 的总和是 300，把它写进 `class = 1`。两个事务各自只 `INSERT`，没有 `UPDATE`，没有唯一约束冲突，写的还是完全不同的行。

如果按串行来跑，先跑 A 再跑 B，B 算出的总和会是 330；先跑 B 再跑 A，A 算出的总和也会变。所以无论哪个顺序，都不可能得到 (30, 300) 这个组合。但在 REPEATABLE READ 下，两个事务都会成功提交。

这里的关键是冲突的位置变了。行锁和唯一索引保护的是"我写的行"。写偏斜里两方写的行互不重叠，行层面永远不会有冲突信号；真正被破坏的是"我读到的集合"与"对方写入的行"之间的对应关系——B 写入的那一行，恰好落在 A 读到过的范围里。这种关系不体现在任何一行的锁上。

PostgreSQL SSI wiki 里的黑白例子把它推到更极端的形式：一张 `dots` 表交替存着 black 和 white，一个事务把所有 white 改成 black，另一个同时把所有 black 改成 white。串行执行时结果必然全同色；并发执行时，颜色被整体交换——一个任何串行顺序都产生不了的状态。两个事务的 `UPDATE` 都带 `WHERE`，行数一样多，谁也碰不到谁。

还有一类更贴近业务的形态，同一份 wiki 用收款批次举过例：事务 T1 往旧批次里插最后一张收款单，T2 关闭批次并把控制表里的批次号加一，T3 在此基础上出存款报表。单看每一步都合理，把三个提交顺序拼起来就形成了环——T3 看不到 T1 的那张单，而 T1 又显得发生在 T3 之后。批次声称已经封账，改动却在之后冒出来。

写偏斜之所以危险，在于它不报错。唯一约束不响、外键不响、行锁不响，应用层看到的是一串成功的提交，错误留在了数据里，几小时后由对账发现。

## 四、谓词锁：不阻塞的锁

真正的可串行化需要对"读到的范围"上锁，学术上叫谓词锁。传统做法会让读操作阻塞写操作，并发度立刻掉一个量级——这也是很多系统宁愿停在快照隔离的原因。

PostgreSQL 的实现是[可串行化快照隔离](https://wiki.postgresql.org/wiki/SSI)（Serializable Snapshot Isolation，SSI），在快照隔离之上加一层冲突检测，而不是加一层阻塞。官方文档对此的描述非常明确：这些谓词锁**不引起任何阻塞，因此不可能参与死锁**。它们只负责标记并发可串行化事务之间的依赖关系，在某些组合下构成序列化异常。

这层"锁"在系统视图里能看见，`pg_locks` 中 `mode` 为 `SIReadLock`。它的粒度不是固定的，取决于查询计划：扫描到元组就记元组级，扫到页就记页级，而且事务进行中多个细粒度锁会被合并成更粗的锁，目的是不让锁表把内存吃穿。这个合并动作在文档里出现两次，第二次是在性能建议里——因为它直接对应失败率。

学术来源是两条线：Cahill、Röhm、Fekete 在 SIGMOD 2008 的 *Serializable isolation for snapshot databases* 提出自动检测并阻止快照隔离异常、同时保持读写互不阻塞的算法，这项工作在 2018 年拿到 SIGMOD Test of Time Award；Ports 与 Grittner 在 VLDB 2012 的 *Serializable Snapshot Isolation in PostgreSQL* 把工程实现落到了 PostgreSQL 9.1。

## 五、pivot：系统在提交那一刻做的判断

SSI 检测的危险结构，落到用户能看见的东西上，是一行错误信息和它的 DETAIL。

还是 `mytab` 那个例子，在 `SERIALIZABLE` 下两个事务都提交时，其中一个会收到：

```text
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Cancelled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.
```

`pivot` 是那个"中间人"事务：它一边被别的事务读过、一边又读了别的事务写的东西，两条反向依赖在它身上接起来，形成一个环。系统认定这里是环的转折点，就在提交时取消它。

取消策略是 **first committer wins**：两个事务都跑到提交，谁先提交谁留下，另一个回滚。这个顺序不是随便挑的，它保证总有事务能推进，并且被取消的那个立刻重试就有很大机会成功——因为它重试时看到的初始视图里已经包含了对方的提交，那个原本不存在的串行顺序现在存在了。

这也解释了那句 HINT 为什么是"might succeed"而不是"will succeed"。重试能不能成功，取决于重试那一刻的并发情况，而不是取决于上一次失败的原因。

## 六、账单：40001、误报与锁的粒度

把隔离级别从 REPEATABLE READ 提到 SERIALIZABLE，多出来的不是锁等待，而是三类成本。

**第一类是重试。** 序列化失败的 SQLSTATE 固定为 `40001`，文档要求应用必须有统一的失败处理路径，因为"哪个事务会被回滚"极难预测。还有一个容易忽略的细节：只有会写的事务才可能因序列化冲突被回滚，只读事务在 REPEATABLE READ 下永远不会有这个问题；但在 SERIALIZABLE 下，只读事务也可能被取消——SSI wiki 的 rollover 例子展示了这一点，只读事务在读取时收到 `Reason code: Canceled on conflict out to pivot`，触发条件是它要读的数据落在了别人已提交的修改范围内。

**第二类是误报。** 文档写得很直白：SERIALIZABLE 只允许那种"能证明存在等价串行顺序"的提交，但它并不能保证只在真正串行执行会出错时才报错。最典型的形态是唯一约束冲突——即使事务在插入前显式查过这个 key 不存在，两个重叠的可串行化事务依然可能撞出约束冲突。规避办法不是加锁，而是让**所有**插入潜在冲突 key 的序列化事务都遵循同一套先查后插的协议；只要有一部分事务绕过协议直插，这套协议就失效。

**第三类是锁的粒度直接换算成失败率。** 这是全篇最像运维账单的一段：

| 触发条件 | 机制 | 结果 |
| ---- | ---- | ---- |
| 谓词锁表内存不足 | 多个页级 `SIReadLock` 被合并为关系级锁 | 序列化失败率上升，可调 `max_pred_locks_per_transaction`、`max_pred_locks_per_relation`、`max_pred_locks_per_page` |
| 查询走了顺序扫描 | 顺序扫描必然需要关系级谓词锁 | 失败率上升，可通过降低 `random_page_cost`、提高 `cpu_tuple_cost` 鼓励走索引 |
| 事务过长、连接闲置 | 依赖链拉长，`SIReadLock` 需要保留到重叠的读写事务结束 | 冲突窗口变大，用 `idle_in_transaction_session_timeout` 兜住 |

第二行值得多想一层：调 `random_page_cost` 和 `cpu_tuple_cost` 是优化器成本参数，为了让 SSI 少报错而改它，代价是查询执行计划本身可能变差。文档也提醒了这一点——要把"减少事务回滚"和"整体查询变慢"放在一起衡量，不要只看一面。

第一行同样反直觉：故障不是来自业务冲突多，而是来自锁表装不下，系统只能把细粒度锁降级成粗粒度锁，于是原本不冲突的事务开始被判为冲突。并发越高，这个降级越容易发生。

## 七、只读事务的特殊待遇

只读事务在 SSI 里有一条专门的捷径。`READ ONLY` 事务如果能在启动时确立"不可能再有冲突发生"，就可以提前释放 `SIReadLock`，实践中很多时候干脆一个谓词锁都不取。

代价是把这件事变成一个需要等待的判断：`SERIALIZABLE READ ONLY DEFERRABLE` 会**阻塞**，直到它能确立这个事实为止。文档特意标注，这是可串行化事务阻塞而可重复读事务不阻塞的唯一情形。

这条捷径的适用场景很清晰——长时间只读、结果必须可靠的作业：逻辑备份、月度对账、离线报表。用一点启动等待，换掉整段读取期间被 pivot 牵连回滚的可能。反过来，一个短查询没有理由用 DEFERRABLE，等待的时间和收益不成比例。

文档还提了一个使用上的前提：从永久用户表读到的数据，在读取它的事务成功提交之前都不能当作有效结果——只读事务也不例外（DEFERRABLE 是唯一例外）。这意味着"读到了就用"这种写法在可串行化下是错的，结果必须等到提交成功那一行日志过去才算数。

## 八、什么时候值得把它打开

把文档里的性能建议和上面的机制放在一起，一个可操作的判断标准大致是这样：

**值得用 SERIALIZABLE 的场合**，是那些不变量跨越了多行、并且无法用单行约束表达的写入路径——账户余额之和、库存与预留量、批次封账、名额上限。这些规则的共同点是：应用必须在读完之后才决定写什么，而读的范围和写的范围必然交叠。

**不值得的场合**是纯单行写入、纯只读查询，以及那些已经用唯一索引或外键精确表达了约束的路径。这些场景里 SSI 的检测不会带来额外正确性，只会带来开销。

决定打开之后，配套动作比级别本身更重要：

1. **声明只读**。会只读的事务标 `READ ONLY`，让系统能提前裁掉谓词锁。
2. **写重试循环**。捕获 `40001`，整段事务重来，而不是只重跑失败的那条语句——重试的语义是"换一个新快照重来"，不是"补一步"。
3. **保证可重试**。事务体内不要有不可回滚的副作用，比如发出邮件、调用支付、写外部日志。
4. **缩小事务**。文档的建议很直接：别把超过完整性需要的东西塞进一个事务，也别让连接长时间停在 `idle in transaction`。
5. **拆掉旧锁**。既然 SSI 已经提供了保证，那些为防写偏斜而加的显式 `LOCK`、`SELECT FOR UPDATE`、`SELECT FOR SHARE` 就不再需要——而它们既会阻塞别人，也会产生磁盘访问。留着它们等于同时承担两种成本。
6. **看住锁表**。并发上来之后回头检查序列化失败率，判断是业务冲突还是锁粒度降级。

第六点容易被当成运维细节，其实它决定这套机制在生产里能不能用。SSI 的正确性不依赖配置，可用性依赖配置。

## 九、小结

回到那张四行五列的表。它没有骗人，只是它的边界画在 1995 年之前。写偏斜不在表里，因为定义这张表的时候，还没有人把它形式化成一行。

快照隔离的问题不是"不够严格"，而是它的严格程度恰好停在了一个很难被察觉的位置：每一行看起来都对，提交日志全是成功，错误藏在了组合里。SSI 的做法也不是把快照隔离换成锁，而是在快照之上加一层不阻塞的依赖追踪，用提交时的取消换取串行等价。

代价是明确的：一个 `40001` 的重试路径、一类可能出现的唯一约束误报、一套需要看住的谓词锁参数。它不便宜，但它保的东西——那些跨行的不变量——在快照隔离下根本没有别的保法。选择隔离级别，本质上是在选择让哪一类错误变成一次可以重试的失败。
