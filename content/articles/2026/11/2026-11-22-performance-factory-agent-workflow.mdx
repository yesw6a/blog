11 月 19 日，OpenAI 在工程博客里写了一件不太像发布会的事：他们把一个性能团队日常做的"慢速排查"改造成了流水线（[How OpenAI's Performance Factory keeps ChatGPT fast](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)，2026-11-19）。

公开的数字很扎眼：这套系统运行三个月出头，Regression Workflow 跟踪了 1700 多次调查，定位到 600 多个问题的根因，平均每天 17 次自动调查。但整篇文章读下来，最值得搬回自己团队的不是这些数字，而是它把"人机协作"拆成了显式状态，并用两套评测把 agent 的质量钉在可回看的地方。

## 从告警到恢复：六个状态，每一步都有负责人

Regression Workflow 的骨架是一条状态链，人和 agent 交替接棒：

| 阶段 | 执行者 | 产出 |
| --- | --- | --- |
| Detected | 系统 | 指标越阈值，开出一个任务 |
| 找根因 | Codex agent | 起变时间、受影响请求、部署与开关变化、相关代码 |
| 提出修复 | Codex agent | 实现改动并提交 PR |
| 审查并部署 | 工程师 | 决定是否合并、必要时自己改 |
| 验证恢复 | Codex agent | 对比部署后指标是否回到基线 |
| Resolved | — | 部分恢复则拆出新任务，无改善则退回调查 |

关键在于任务的**状态与结论存在 agent 上下文之外**。这样工作可以在 agent 之间、agent 与工程师之间转手，也能在代码评审或部署等待期间挂起，之后再接着做。这是"工厂"和"自动化脚本"的分界：脚本要求一次跑完，工厂允许一项工作跨越多个人、多个 agent 和几天的排队时间。

## 为什么"把告警丢给 Codex"不够

官方把演进路径列成了六级，每一级都卡在同一个问题：谁来决定下一步。

1. **前 Codex 时代**：人翻指标、日志、trace、抓 profile、读代码。定位靠对服务的熟悉度，信号容易漏掉。反复遇到同类问题（比如首个 token 延迟退化）后，团队攒下了 30 多个性能工具。
2. **Codex 当搭子**：工程师问"为什么变慢了"，Codex 搜代码库、找指标和 trace、跨服务追交互、做 profiling。但人仍然要指挥，要决定用哪个工具、往哪儿查。
3. **可复用技能**：把排查方法论写成 `perf-forensics` 技能——告诉 Codex 有哪些工具、什么时候用、怎么从"起变时间、受影响请求、部署或配置变化"几个角度推。技能本身用历史事故回测来打磨。
4. **人肉代理**：有了技能之后，工程师变成了告警和模型之间的转发器，复制粘贴进 Codex，再把结论粘回 Slack。
5. **自动调查**：把会话搬到云端，告警直接起一个 Codex 会话，结论发到 Slack 线程。但自动化止步于"回复"，诊断之后的修复和验证还在人身上；告警一多，光判断哪条要紧就得翻线程。
6. **工厂**：任务服务记录每项工作下一步需要什么，调度循环在就绪时分配 agent，任务带着状态和发现往下走。

第 4 级是最容易停下来的地方——它看起来已经省了力气，实际只是把人变成了接口。真正产生量变的是第 5 到第 6 级：把"谁来推进"从人脑转移到任务状态上。

## 工厂的四个零件

系统由四部分组成，实现都不复杂，难的是边界：

- **任务服务**：工程师用 Markdown 配置文件定义工作流，声明任务能经过哪些状态、允许哪些转移、哪几步必须由工程师处理，每个状态再配一段给 agent 的提示词。所有任务在一个界面上可见，可转交给更熟悉上下文的同事。
- **调度循环**：周期性检查哪些任务就绪，为每项启动一次 Codex 会话，完成后由 agent 记录进展并推进状态。
- **云端执行**：内部 API 在网络内拉起 Codex 会话，让它访问仓库和工程师平时用的可观测工具——指标、日志、trace、CPU profile、内存快照。agent 以服务身份运行，权限可被限定，也能追溯哪些动作来自性能 agent。搬上云之后，并行不再依赖谁的笔记本开着。
- **事件订阅**：需要等人的时候，任务订阅 GitHub 评审评论、CI 失败、部署完成这类事件；事件一到，任务重新就绪，调度循环再派 agent 接着做。

这个组合回避了一个常见坑：不要让 agent 长时间空等。等待是人或外部系统的事，agent 只需在事件发生后被唤醒。

## 对抗审查：让另一个会话来推翻结论

早期 agent 常常停在"第一个看起来合理的解释"上，其中一部分是错的。于是团队加了一步对抗审查：单独开一个 Codex 会话，专门去证伪。

评审者会重查假设、构造反事实——如果问题真是某次灰度造成的，那批没被放量的相似请求是不是还健康？如果嫌疑改动已经回滚，指标有没有回来？

文中给了一个具体例子：某次 agent 把失败的对话归因到图片下载错误，并标记为已找到。评审会话发现，负责定位文件的内部服务其实早已恢复，而图片请求仍在失败——这条诊断解释不了持续存在的故障，于是重新打开调查，并写下还缺哪些证据。

官方同时公布了准确率口径：人工复审 100 条根因建议，70% 判为准确，30% 需要进一步细化或没能完整建立因果。这个数字值得记住，它说明这类系统目前的状态是"高吞吐的初筛"，不是"可信的判决书"。

修复这一环更难。团队遇到过 agent 把改动写得比必要的复杂，或引入新问题；于是每个修复提案同样加一轮对抗审查。还有一类是架构取舍，比如加缓存能提速但会引入陈旧数据，这种只能由懂服务的人来权衡。

## 三条可以立刻借用的经验

**第一，保护工程师的注意力，而不是提高 agent 的吞吐。** 第一版给了工程师一个满是发现的界面，结果仍然要人来判断哪些重要。一个退化可能以多条告警的形式散落在不同监控和频道里，所以现在的流程会合并相关事故、按团队关心的指标分组、按影响排序。agent 能查的回归数量远超团队阅读能力，瓶颈很快从调查转移到阅读。

**第二，把 agent 的评测拆成两件事分别做。** 一件是"查得准不准"：把历史生产事故做成可重跑的测试集，每次改技能或换模型都跑一遍，并且给 agent 换一个全新会话、去掉可能泄题的细节。历史数据评测有两个陷阱——指标和 trace 会过期，事后收集的证据会直接暴露答案；因此要明确它能看什么（代码、限定范围内的生产遥测）、不能看什么（历史调查笔记、事故复盘文档、上一次运行的结果），事后还要检查会话记录有没有被污染。评分也拆开：起变时间、影响范围、受影响请求，各算各的——一个 agent 完全可能时间点对、却怪错了部署。

另一件是"交接说得清不清"：用保存下来的任务快照做回测，因为摘要不依赖会过期的外部数据。由单独的评审判断一个不了解该系统的工程师能否看懂发生了什么、为什么重要，图表有没有保留，下一步是否有证据支撑。

**第三，让 agent 自己也需要被监控。** profiler 坏掉、权限缺失，都会让 agent 卡在某个步骤，而这些失败在最终报告里很难看出来。团队每天跑一个 agent 专门扫最近的运行消息和日志，找工具失败和访问错误；同一个工具错误卡住多起调查时，就开任务修它，修完再用评测确认 agent 能否越过原先那道坎。

## 这些数字该怎么读

有三点需要明确限定：

- **1700 次调查不等于 1700 次修复。** 600 多个是"定位到根因"，PR 是否合并、修复是否真的解决线上问题，是另外的口径。文中明确说，目前的瓶颈常常是等工程师审查合并。
- **70% 来自 100 条建议的人工复审。** 样本量不大，评分者也来自同一团队，属于自报口径。它足以支撑"可作为初筛"的判断，不足支撑"可以无人值守"。
- **每天 17 次是按三个月出头的总量折算**的均值，不含分布信息：真实负载大概率是尖峰式的，而排队的恰恰是人的审查时段。

## 下一步是主动发现，以及一个没说死的边界

文末描述的方向有三个：一是在没有告警的情况下，用已有的 CPU/内存 profile、堆转储、跨版本请求 trace 去找告警漏掉的退化和优化点，发现后直接在 Regression Workflow 里开任务；二是把已知信号固化成可日常运行的工作流，比如一个 `service rightsizing` 技能专门揪出副本数开过头的自动伸缩配置；三是让一个工作流的 agent 给另一个工作流开任务，形成跨流程协作。

至于"agent 自己合并修复"这件事，文中的措辞仍是探索：先识别低风险改动，再看能否无人在环地发出去。眼下这条链的终点仍然握在工程师手里，而这恰恰是它还能被信任的原因。

对服务团队来说，可迁移的最小集是四件事：任务状态外置、等待靠事件唤醒、结论要有对抗审查、以及把"查得准"和"交接清"分开评测。先做对第一条和第四条，agent 的吞吐才算真正可用。
