过去两年，模型能力的提升基本沿着一条路线走：加参数、加数据、加算力。这条路线的账单很直白——每一份能力都要用显存和推理成本来换。11 月 23 日晚间发布的 GLM-5.4 走的是另一条路：参数量几乎没动，让网络把同一组层多跑几轮，用计算深度换智能上限。

据[智谱官方技术博客](https://www.zhipuai.cn/zh/research/164)，GLM-5.4 基于约 7500 亿参数规模的基座，首次采用 Loop Transformer 架构，官方称其智能水平可达到 2 万亿至 3 万亿参数级模型的效果。配套信息来自[上海证券报的报道](https://www.cnstock.com/commonDetail/832502)：GLM-5.4 即日起向 GLM Coding Plan 全量用户开放，同步上线 ZCode、Trae、WorkBuddy 等编码平台，API 将在完成安全评估后开放，模型权重计划后续开源。

这不是一次普通的版本迭代。它把"深度"从"层数"里拆了出来，也因此把过去被层数锁死的几笔工程账重新翻开了。

## 一、被参数绑定的那条路

标准 Transformer 的计算图是固定的：每一层前向计算一次，第 N 层用完就再也不参与。想让它想得更久，只能加层；加层意味着加参数；加参数意味着显存、带宽、单次推理成本一起上涨。

这条约束在预训练阶段还不太刺眼，因为那时候大家比的是同等算力下的效果。但到了推理和部署阶段，参数量几乎直接换算成了账单：模型多大，权重就多大，能同时驻留多少请求就定了上限。

Loop Transformer 换了一种记账方式。按官方描述，它让一组共享权重的网络层循环执行多轮，每一轮在上一轮输出的隐状态基础上继续推演、细化。参数量不增加，但因为同一组层参与了更多次计算，模型等效地获得了一个更深的网络。

这里有个容易混淆的点，值得先说清楚：**Loop 不是把模型层数翻倍再共享权重**。官方博客明确讲了取舍——权重共享能提高参数效率，但在同等预训练计算量下，效果仍然不如不共享权重的模型。所以他们没有从头预训练一个 Loop 模型，而是把一个**已经完成预训练**的基座模型，通过进一步训练改造为 Loop Transformer，用较小的算力开销换取智能上限。

这个选择的意味比架构本身更重。它说明 Loop 是一种"改造"手段，不是"重训"手段：已经在跑的基座不必作废，可以在其上加一轮结构改造。对一家需要持续交付模型的团队来说，这比从零训练一个新架构现实得多。

## 二、28 层走两轮，坑在第一次覆盖

GLM-5.4 的做法是对 GLM-5 基座中的 28 层做两轮循环。听起来只是把中间一段跑两遍，但官方博客点破了朴素实现会撞上的第一个问题。

把已有模型的中间层改成多轮循环时，如果直接用每轮输出覆盖隐状态，激活范数（activation norm）会随循环轮数过度膨胀，后续层接收到的表示也会偏离原模型熟悉的尺度和分布。换句话说，原模型的后续层是按"这一层输出大概长这样"训练出来的，你让它连续接收两次放大后的信号，那些层的先验就失效了。

Loop 要成立，必须让第二轮写回残差流的东西，尺度上仍然像第一轮。这是整篇文章里最"工程"、也最容易被跳过的一处：架构图上只是多了个循环箭头，实际要解决的是一整套数值稳定性和分布对齐的问题。

## 三、门控渐进更新：让两轮自己分工

官方的解法是为每一轮设置独立的、逐 token 的门控，按比例把该轮的候选变化写回残差流，而不是整体覆盖。

训练之后，这些门控呈现出清晰的分工：第一轮侧重建立全局上下文状态，对多数位置只以较小的门值温和写回，以稳住尺度；第二轮复用这个状态完成精炼，并放开门控、充分写回结果。

用更直白的话说：第一轮先"通读"，改动小；第二轮"定稿"，改动大。这个分工不是人工设定的，是训练出来的，博客原文写的是"训练后的门控呈现出清晰的分工"。

门控还有一层动态：它会根据 token 的预测难度调节步长。在更难预测的位置，首轮的写入会适度加大，让复杂预测更充分地受益于多轮迭代；在简单位置则保持克制，不浪费一次循环的表达能力。

这一处设计的信息量在于，它把"多算一轮"变成了条件计算：不是所有 token 都值得想两遍，门控在逐 token 决定要想多深。这与混合专家（MoE）的稀疏激活在思路上是同源的——不追求全量满配，追求把算力花在需要的地方。

## 四、KV Cache：多想一轮，几乎不多占显存

Loop 的第二笔账是显存。

朴素做法是为每一轮循环保留一整份 KV cache，显存随循环轮数成倍增长。对 1M 长上下文来说，这个代价基本等于把方案否掉。

GLM-5.4 的处理是跨轮共享 KV，再用滑动窗口补充新一轮的局部信息：第二轮复用第一轮选出的稀疏 KV，同时保留滑动窗口内由第二轮生成的 KV。两路 KV 可以覆盖同一位置，让模型既能读取第一轮的上下文表示，也能利用第二轮更新后的局部表示。

于是多一轮循环的额外代价是"一个窗口的 KV"，而不是"一整份全上下文 cache"。官方给的说法是，在 1M 长上下文下，这个设计让 GLM-5.4 相对上一代 GLM-5.3 的部署成本增幅保持可控。

这里的设计直觉值得留意：第二轮的增量信息主要是局部的。既然第一轮已经把全局状态建好了，第二轮真正需要重新计算的，是窗口内那部分近处细节——远处的上下文表示没必要重算一遍。把"哪些信息需要重算"这个问题答对，显存账单就自然降下来了。

## 五、索引复用：不重复付检索的钱

第三笔账藏在基座采用的稀疏注意力里。

GLM-5.4 的基座使用稀疏注意力，需要一个索引器来挑选哪些 KV 参与计算。循环跑第二轮时，自然的选择是用第二轮更新后的表示重新算一遍索引；但那样一来，每多一轮就多一份索引器开销，而且这份开销随上下文长度增长。

GLM-5.4 的做法是第二轮直接复用第一轮索引器生成的索引，不增加任何索引器开销。官方给的实验结论是：它与每轮重新计算索引的效果几乎相当。

三笔账放在一起看，Loop 的成本结构就清楚了：

| 成本项 | 朴素 Loop 实现 | GLM-5.4 的处理 | 效果 |
| ---- | ---- | ---- | ---- |
| 隐状态尺度 | 每轮输出直接覆盖 | 逐 token 门控按比例写回 | 避免激活范数随轮数膨胀 |
| KV Cache | 每轮一份全上下文 cache | 跨轮共享 + 窗口独立 | 额外代价降为一个窗口 |
| 稀疏注意力索引 | 每轮重新计算 | 第二轮复用第一轮索引 | 索引器开销零增量 |

这张表也解释了为什么 Loop 这类"结构上很小"的改动，落地时往往是三个团队的工作量。多一条循环边是免费的，让这条循环边在多轮之后仍然稳定、仍然便宜，才是难点。

## 六、怎么证明它不是小模型上的幻觉

架构创新最危险的地方在于：小规模上有效、放大之后失效。官方博客对此的表述是一句很重的话——Loop 也是对 Scaling Correctness 的一次严苛检验，任何架构创新必须在规模放大后依然成立。

他们的验证方式是逐级放大：从 1B、4B、30B 一直到 750B 基座，一级一级做验证，然后把旗舰押在 Loop 上。

最能说明问题的是同参数量对照实验。他们在一个与 750B 基座架构完全相同的 30B 模型上做对比：参数量完全相同，整体训练计算量仅增加约 10%，Loop 版本相对基线有明显提升。

这个实验的设计意图很清楚——如果对照实验里参数量不同，提升可能来自"模型更大"；计算量不同，提升可能来自"训练更久"。把参数锁死、只增加约 10% 的计算量，能归因的就只剩下计算深度这一个变量。

需要说明的是，官方博客没有给出这个 30B 对照实验的具体基准名称与分数，只给出了"明显提升"的定性结论。因此本文不引用任何具体的对照分数——那部分数字目前在公开材料里找不到可核验的出处。

## 七、少想几步，想得更深

推理侧的数据更反直觉。

在与 750B 基座完全相同的 30B 模型上，经过 200K 长文本 SFT 后开启 thinking 评测，官方给出两个结论：

第一，推理链越长，Loop 的帮助越大。提升最明显的三类任务是数学推理、长上下文和代码——都是需要"想很久"的任务。

第二，Loop 用更少的 token 完成思考。在 GPQA、MMLU-Pro 等基准上，平均输出长度下降 10% 到 14%，缩减主要来自思维链。

这两条合起来是一个很有意思的组合：既提升了需要长推理的任务，又缩短了思维链的长度。通常我们会认为这两者此消彼长——想让模型想得更清楚，就让它多想几步。Loop 提供的是另一种可能：不是想得更多，而是每想一步算得更深。

官方博客里还有一个观察，模型容易进入"雷霆大思考"模式，即长时间程任务里持续反思。这个描述没有配套的量化数据，更像是一线观察，读的时候应当按观察而非结论来对待。

吞吐方面，官方给出的数字是：非高峰时段速度最高 200 token/s，高峰时段 70 到 80 token/s。循环带来的额外开销，官方称通过结构（按距离拆分 KV cache、稀疏注意力索引复用）和算子融合压到了最低。

## 八、泛 Coding：代码成了多模态的接口

GLM-5.4 的另一个主张是"泛 Coding"：代码不再只是软件开发的产物，而是模型操作视觉内容的通用接口。

官方给出的几个例子值得具体看一下：

- **代码生成视频**。GLM-5.4 做了一个自述 MV「Hello world」。创作者 Mike Luan 用 GLM-5.4 完成创意、编曲、动态与画面渲染的全流程：画面全部由前端代码实时绘制，零素材；音乐由 GLM-5.4 根据章节和镜头自行计划、调用第三方音乐生成模型制作，并自主修改多轮 prompt。
- **代码做工程设计**。GLM-5.4 通过 FreeCAD 构建六轴机械臂模型，调用 Blender 设计动作、做可视化，合成音频，生成抓取 Logo 动作的模拟与可视化。

官方称在 200 个真实场景的编程评测中，GLM-5.4 在视觉 Coding、视觉复刻、长程任务上表现突出。这些评测的具体题目和评分标准没有公开，所以"表现突出"只能作为厂商自述来读。

不过这条方向本身有一个可验证的推论：如果代码真的是多模态生成的通用接口，那么这条路径的瓶颈就不在视觉模型，而在代码模型的长程一致性和工程约束理解上。它把视频、3D、游戏这些原本需要专用模型的任务，归到了一个已经有很多成熟评测和工具链的战场上——这对工程团队是好事，因为可调试性大幅提高；对专用模型则是压力，因为它们原本的护城河是"别人做不了"。

## 九、三条可以带走的判断

把官方材料读完之后，有几条判断值得单独记下来。

**第一条：参数量不再是唯一的能力刻度。** GLM-5.4 用约 7500 亿参数做出官方所称 2 至 3 万亿参数级的效果，两者的差距就是计算深度的定价。这并不意味着参数不重要，而是意味着"参数—能力"的换算关系开始出现第二个自变量。以后看到参数规模时，需要同时问一句：它跑了几轮。

**第二条：结构创新的成本主要不在结构上。** 一个循环箭头几乎不花钱，门控、KV cache、索引复用这三件事才是真正的工程量。评价一个架构改动时，看它的论文/博客里有没有认真交代这三笔账，比看架构图更有判据价值。

**第三条：改造优于重训。** 官方明确说没有从头预训练 Loop 模型，而是把已预训练的基座改造过来。这条路径对资源有限的团队更有参考意义——如果手上有已经跑通的基座，架构改造的试错成本远低于重新预训练。当然前提是改造过程要解决前面提到的分布对齐问题，这不是改个配置文件能完成的。
