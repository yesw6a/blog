2026 年 11 月 16 日，阿里巴巴发布新一代基座模型 Qwen4-Max：总参数 2.4T，采用基于 Qwen 稀疏注意力（QSA）的 MoE 架构，每 token 仅激活 71B，支持百万上下文与原生视觉能力（[中国证券网报道](https://www.cnstock.com/commonDetail/828899)、[腾讯新闻·中经记者报道](https://news.qq.com/rain/a/20261116A0BJ4F00)）。

发布里最值得注意的不是参数，而是定价：**缓存命中每百万 tokens 低至 0.5 元，完成单任务的平均费用相比 Qwen3.8-Max 降低 58%**。同一批报道里还有一个数字，Qwen4-Max 每个 token 的激活参数比上代少了 25%。

这两件事放在一起说明一个变化：长上下文竞争的主战场，已经从"能不能塞进 100 万 token"，转到"塞进去之后每 token 要花多少算力和显存"。上下文越长，KV 缓存、注意力计算、状态存储这三项开销就越不成比例地放大，模型能力本身反而不是瓶颈。

11 月初有三篇论文，恰好各自打在这条链的一个环节上。它们不解决同一个问题，也不互相替代，但拼起来能看出长上下文推理现在的真实工程图景。

## 三堵墙，三种解法

把一个 100 万 token 的请求跑完，阻碍从前往后依次是：

1. **容量墙**：KV 缓存随序列长度和并发数线性增长，很容易顶穿 HBM 容量上限，并发度被迫压到很低。
2. **选择墙**：即便有足够显存，密集注意力在 prefill 和 decoding 阶段都太贵；稀疏注意力能省，但大多数方法要为每个 query 打分所有历史块，选择成本本身就是 O(L)。
3. **结构墙**：把注意力线性化、用固定大小的循环状态替代 KV，确实能省内存，但状态容量有限，长上下文检索会掉点。

三篇论文分别叫 FlashOffloading、RecSA 和 Anchor，下面逐个拆。

## 路线一：把 KV 缓存整体挪到主机内存

**论文：** FlashOffloading: Low-Latency KV Cache Offloading for Long-Context LLM Serving（[arXiv:2611.07542](https://arxiv.org/abs/2611.07542)，2026 年 11 月 5 日）

把 KV 缓存卸载到主机 DRAM 是个很直觉的思路：HBM 腾出来了，并发自然上去。但真实系统里这一步常常不划算——缓存管理本身有开销，H2D（主机到设备）加载有延迟，并发上去了，有效吞吐却没跟上，因为每个 token 的等待时间被拉长了。

FlashOffloading 的做法是**以主机 DRAM 为中心重构整个推理路径，prefill 和 decode 两个阶段的 KV 缓存全部卸载**，然后用四个机制收紧延迟：

- **滚动 HBM 缓存**：prefill 阶段不再要求整段 KV 常驻 HBM，只保留一个滑动窗口式的工作集。
- **decode 热缓存**：解码阶段单独维护高频访问的缓存片段。
- **反向稀疏索引**：关键在于"零额外未命中查找开销"——把查找成本提前摊到索引结构里，而不是在每次访问时再算一遍。
- **计算-加载重叠 kernel**：把 H2D 传输和计算并行，让搬运时间藏进计算时间里。

实验结果是用 GLM-5.2（带 MTP3 多 token 预测投机解码）部署在**昇腾 910C 的 PD 分离平台**上：在 30ms TPOT 的服务等级目标约束下，**prefill 吞吐最高提升 1.38 倍，decode 吞吐最高提升 1.91 倍**。论文明确说明该方案已集成进一个开源服务框架。

这条路线最值得记的一点是评价口径：它报的不是裸吞吐，而是"在 TPOT SLO 下的吞吐"。卸载类方案的常见陷阱就是拿忽略尾延迟的平均吞吐说事，而对在线服务来说，P99 的 token 间隔才是用户真正感受到的东西。

## 路线二：让选择成本降到对数级

**论文：** Recursive Sparse Attention: Million-Token Length Extrapolation at Logarithmic Cost（[arXiv:2611.07232](https://arxiv.org/abs/2611.07232)，2026 年 11 月 4 日）

稀疏注意力的通病被这篇论文点得很准：大多数方法要为每个 query 给所有前序 block 或 token 打分，在长度 L 下每次选择就是 O(L)。层级化选择能把选择成本降到 O(log L)，但**此前可训练的层级方法只在训练长度内报告过精度**——也就是说，"便宜"和"能外推"这两件事一直没能同时成立。

RecSA 在 KV 缓存上建一棵树，每个节点用一个 key 和一个 mean-pooled value 概括整个子树。三个设计细节决定了它能不能真的用：

**池化器只有一层一份。** 每个层只有一个 pooler，所有层级共用它，且这个 pooler 是从密集注意力里蒸馏出来的。这避免了层级越多、池化器越多、训练越难收敛的问题。

**每层最多选 k 个候选。** 树上每一层（token 之上）的选择上限是 k，于是每个 query 的选择成本是 O(log L)，实际读取的条目数也是 O(log L)。未被选中的候选，其摘要与精确 token 共用同一个 softmax——不是两套注意力拼起来，而是同一次归一化。

**RoPE 位置按候选序号重排。** 每个条目的 RoPE 位置取它在本层候选中的索引。这一步的作用是让任意长度下的相对距离都落在训练时见过的范围内，这是长度外推能够成立的关键。

训练配置很克制：从 Qwen3-4B 初始化，在原模型 32K 训练长度上只用 0.62B token 训练。效果是 RULER 在 131K 到 2M 的每一个长度上都优于全部基线；**1M 长度上得分 60.5，最好的基线 Dense + DCA 是 40.0**。配合优化后的 kernel，端到端 prefill 与 decoding 在 64K 到 2M 区间都快过密集注意力；**在单张 H200 上跑 524K 上下文，prefill 加速 3.2 倍，decoding 加速 3.8 倍**。

注意这里"只训练 0.62B token"的意义：想做长上下文的团队不必重训一个基座，用少量 token 就能给已有模型接上百万级能力。这对开源模型生态的杠杆，比榜单分数本身更实际。

## 路线三：不是每一层都需要记住东西

**论文：** Anchor: Augmented Cross-Layer Recurrent State for Long-Context Retrieval in Test-Time Training（[arXiv:2611.04327](https://arxiv.org/abs/2611.04327)，2026 年 11 月 3 日）

参数高效的线性化方案通常这么干：把预训练的自回归 Transformer 改成滑动窗口注意力（SWA）加一个固定大小的循环记忆，混合成高效模型。省是省了，但长上下文检索能力会掉。

这篇论文先问了一个更基础的问题：**每一层的循环状态都对长上下文检索有贡献吗？** 作者在一个 SWA 与 Test-Time Training（TTT）的混合结构上做探查，得到两个观察：

- 检索能力在深度上是**稀疏的**，集中在少数几层，作者称之为锚点层（anchor layers）。
- 其余层的状态承载的信息其实差不多，只是各自通过层特有的变换来表达。

Anchor 直接利用这两个观察：TTT 记忆只放在锚点层；跨层维护一份循环状态，**写一次、多层共读**，每层通过自己学到的 read map 去读——这个 read map 实现的是一次层特有的拉伸与旋转。论文还报告了该思路对其他混合注意力的泛化。

在 Llama-3.1-8B 和 Mistral-7B 上，相比 LoLCATs，Anchor 的**检索召回高 2.3 到 3.1 倍，MMLU  accuracy 高 6.7 到 8.9 分，而循环状态小 10 倍**；保留了 teacher 模型 91% 到 95% 的 MMLU 精度，端到端延迟相比 softmax 注意力降低最多 4.3 倍。

"状态小 10 倍还更准"这个组合说明，之前线性化方法的损失很可能不全是容量不够，而是**把容量平均分配给了不需要它的层**。层间冗余没有被利用，才是浪费的根源。

## 三条路线的分工与代价

| 维度 | FlashOffloading | RecSA | Anchor |
| ---- | ---- | ---- | ---- |
| 打的墙 | 容量墙（HBM 装不下） | 选择墙（注意力太贵） | 结构墙（状态装不下语义） |
| 改动层次 | 服务系统与显存层级搬运 | 注意力选择算法 | 模型层结构与记忆分配 |
| 是否需重训 | 不需要 | 需少量训练（0.62B token，32K） | 需训练 read map 与 TTT 层 |
| 关键数字 | 30ms TPOT 下 prefill 1.38x / decode 1.91x | RULER 1M 60.5 vs 基线 40.0 | 状态小 10x，召回 2.3-3.1x |
| 主要代价 | 依赖 H2D 带宽，kernel 与索引复杂度高 | 依赖池化器蒸馏质量与树结构 | 依赖锚点层的识别是否稳健 |

三者并不冲突。一个真实的服务栈完全可能同时用上：模型侧用 RecSA 或 Anchor 把单请求的注意力成本压下来，系统侧用 FlashOffloading 把剩下的 KV 缓存放到更便宜的存储层，最后用 PD 分离把 prefill 和 decode 的硬件诉求拆开。

## 几点判断

**第一，长上下文的单位成本正在成为产品定义的一部分。** Qwen4-Max 把缓存命中价压到 0.5 元/百万 token，并强调单任务成本降 58%——这类定价只有在 KV 缓存复用和显式缓存命中机制成立时才可能维持。上面三篇论文讲的都是同一件事的不同侧面：谁能让"记住"这件事更便宜。

**第二，可训练稀疏注意力在 2026 年下半年开始真正可用了。** 此前瓶颈不是稀疏本身，而是在训练长度之外精度崩掉。RecSA 用 RoPE 位置重排这个相对轻的手段解决了外推，这条路线的边际成本比"重训一个长上下文基座"低太多。

**第三，"稀疏分配"是对称出现的。** 一层里只有部分 KV 重要（RecSA 的候选选择），网络里只有部分层承载检索（Anchor 的锚点层）。两篇论文独立得出同一个方向的结论，说明冗余是结构性的，不是训练不充分。对做推理优化的团队，这意味着任何"对所有层、所有 token 一视同仁"的方案都还有余量可挖。

需要提醒的是，以上数字都来自论文作者自测环境，评测基准（RULER、MMLU）与真实业务的请求分布差距不小。昇腾 910C 上的 1.38 倍和单卡 H200 上的 3.2 倍，不能直接换算成你线上集群的收益。真要落地，第一步永远是拿自己的流量分布做一次小规模对照。
